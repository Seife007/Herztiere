## Entscheidungen & Begründungen

- Kontext-Automatisierung über Hooks statt nur CLAUDE.md-Instruktionen, weil reine Textanweisungen nicht zuverlässig durchgesetzt werden (memory.md könnte vergessen werden). SessionStart-Hook injiziert `memory.md` automatisch, Stop-Hook erzwingt Aktualisierung bei uncommitteten Änderungen.
- SSH statt HTTPS für GitHub-Auth gewählt, da `gh` CLI auf diesem System nicht installiert ist und kein Credential-Helper für HTTPS eingerichtet war.
- GitHub-Issue-Zugriff über einen vom Nutzer bereitgestellten Personal Access Token per `curl`, da `gh` CLI nicht installiert ist. Token lokal außerhalb des Repos gespeichert (`~/.herztiere-github-token`, chmod 600).
- Issue #1 wurde vollständig (inkl. Recherche, Scaffold, Migration, Doku) abgearbeitet, bevor mit Issue #2 begonnen wird, statt mehrere Issues parallel oberflächlich anzufangen – alle Folge-Issues bauen explizit auf #1 auf, und schlechte Grundannahmen hier (z. B. falsches DB-Schema) wären teuer zu korrigieren.
- Auth-Status per JWT in httpOnly-Cookie statt im Frontend-JS-zugänglichen Storage (z. B. localStorage), um das Token vor XSS zu schützen. Middleware verifiziert das Token UND lädt den User live aus der DB (statt nur dem Token zu vertrauen), damit Sperren/Löschen sofort wirken, nicht erst nach Ablauf des Tokens.
- `users.deleted_at` (aus Issue #1) wieder entfernt: sowohl Self-Service- als auch (künftige) Admin-Löschung sind als harter Delete umgesetzt, nicht als Soft-Delete – das entspricht dem DSGVO-Löschungsrecht aus Issue #7 direkter als eine nur markierte, aber weiter gespeicherte Zeile.
- Passwort-Reset-Token wird gehasht (SHA-256) in der DB gespeichert, nie im Klartext – gleiches Prinzip wie bei Passwörtern selbst, falls die DB kompromittiert wird, sind Reset-Links nicht direkt nutzbar.
- Kein echter E-Mail-Versand für den Passwort-Reset angebunden (kein SMTP-Account vorhanden/konfiguriert) – bewusste Scope-Entscheidung, um Issue #2 nicht an einer fehlenden externen Abhängigkeit aufzuhalten. Der Reset-Link wird stattdessen geloggt, der Flow ist dadurch vollständig end-to-end testbar.
- Tailwind v4 (statt v3) verwendet, da das aktuell von `create-vite` installierte Tooling und `npm`-Registry-Standardversion Tailwind v4 ist (`@tailwindcss/vite`-Plugin statt `tailwind.config.js` + PostCSS).
- Override-Mechanismus für Tiere als ein flexibles `overrides` JSONB-Feld + `manually_edited`-Flag statt einzelner Override-Spalten pro Feld, für einfachere Erweiterbarkeit in Issue #3/#5.
- `source_url` bei Tieren zeigt auf die RSS-Feed-URL selbst (keine stabile Detailseite pro Tier in der Quelle vorhanden); Zuordnung erfolgt über `external_id` (= RSS-GUID).
- Bild-Handling (Issue #3): eigenes Caching statt Hotlinking gewählt (wie in der Issue-Beschreibung empfohlen), damit die App nicht von Verfügbarkeit/Ladezeit von wien.gv.at abhängt. Speicherstrategie: lokales Dateisystem (`IMAGE_STORAGE_DIR`, Default `backend/storage/images/`) statt Objekt-Storage, da für die aktuelle Datenmenge (~190 Tiere) und den Entwicklungsstand ausreichend und ohne zusätzliche externe Abhängigkeit; bei Bedarf später auf Objekt-Storage migrierbar, da der Zugriff über die gekapselte `imageCache.ts` läuft.
- Override-Schutz beim Sync strukturell statt per Feldliste umgesetzt: Die reine Merge-Funktion (`syncPlan.ts`) kennt die Felder `overrides`/`manually_edited`/`is_hidden` gar nicht und die DB-Schreibfunktionen (`sync.ts`) referenzieren sie nirgends – ein versehentliches Überschreiben ist dadurch nicht nur unwahrscheinlich, sondern (ohne Codeänderung an diesen Stellen) unmöglich.
- Reaktivierungslogik: ein zuvor auf `removed` gesetztes Tier wird beim Wiederauftauchen im Feed automatisch auf `active` zurückgesetzt. Ein manuell auf `adopted` gesetztes Tier (Admin-Aktion, Issue #5) wird vom Sync nie automatisch verändert – weder reaktiviert noch entfernt – da das eine bewusste redaktionelle Entscheidung ist, die der automatische Abgleich nicht überstimmen soll.
- `POST /api/admin/sync` läuft bewusst synchron (kein Background-Job/Queue), da die Datenmenge (~190 Einträge, ~10s Laufzeit) das für den aktuellen Umfang unproblematisch macht und ein einfacher Request/Response-Zyklus für Issue #3 ausreicht.
- Animals- & Likes-API als eigene Services/Routes gebaut, obwohl kein Issue sie explizit vorsieht: Issue #4 (Frontend) braucht zwingend Daten aus der DB, und ohne diese API wäre das Frontend nicht baubar. Bewusst schlank gehalten (kein Pagination/Filtering über das für den Swipe-Stapel/die Merkliste Nötige hinaus) statt vorab eine größere Admin-taugliche API zu bauen, die eigentlich erst in Issue #5 gebraucht wird.
- `isLiked` gezielt nur bei `findAnimalById` per EXISTS-Subquery berechnet (nicht bei der Swipe-Liste, wo es immer `false` ist, oder der Merkliste, wo es immer `true` ist) – vermeidet einen unnötigen Join/Subquery in den beiden Fällen, wo das Ergebnis ohnehin feststeht.
- Swipe-"Überspringen" wird bewusst **nicht** serverseitig persistiert (kein `skips`/`passes`-Table, nur `likes` existiert seit Issue #1) – übersprungene Tiere können in einer späteren Session erneut auftauchen. Das ist eine bewusste Scope-Entscheidung für Issue #4 (kein Issue verlangt explizit ein Persistieren von "nicht interessiert"); falls das gewünscht ist, wäre das ein eigenes späteres Issue/eine Migration.
- Selbstlöschung im Frontend mit einem inline Bestätigungsschritt (Button → "Wirklich löschen?" mit Bestätigen/Abbrechen) statt einem Modal-Dialog umgesetzt – einfacher umzusetzen, kein zusätzliches Modal-System nötig, erfüllt aber die Anforderung "mit Bestätigungsdialog" aus Issue #4 inhaltlich.
- Bei der Live-Browser-Verifikation von Issue #4 wurde bewusst kein `chromium-cli` (nicht installiert) und keine gebündelten Playwright-Browser (auf diesem Debian 11 nicht unterstützt) verwendet, sondern das `playwright`-npm-Paket direkt gegen den vorhandenen System-Chromium (`/usr/bin/chromium`) – siehe "Offen/nächste Schritte" für das genaue Vorgehen, falls in einer späteren Session erneut Browser-Tests nötig sind.
- Admin-Bereich (Issue #5) bewusst als eigenes React-Layout (`AdminLayout`) statt innerhalb des öffentlichen `Layout` umgesetzt, weil die Issue-Vorgabe explizit ein vom öffentlichen Design unabhängiges, funktionales Dashboard verlangt. Dafür `App.tsx` umstrukturiert: öffentliche Routen laufen über eine `PublicLayout`-Wrapper-Route statt einer global umschließenden `<Layout>`.
- Letzter-Admin-Schutz als reine, DB-lose Funktion (`blocksLastAdminDemotion`) statt Inline-Logik in der Route implementiert, damit die sicherheitsrelevante Regel per Unit-Test ohne Postgres abgesichert werden kann (Konsistenz mit dem bereits etablierten Muster reiner Funktionen wie `computeSyncPlan` aus Issue #3).
- Tier-Overrides (Issue #5) als vollständiges Ersetzen des `overrides`-Objekts umgesetzt (`PATCH /api/admin/animals/:id` mit `{overrides, isHidden}`), nicht als Merge/Patch einzelner Felder – das Frontend verwaltet den kompletten Override-Zustand clientseitig (pro Feld an-/abhakbar) und schickt ihn geschlossen. Einfacher als serverseitiges Patchen einzelner Override-Keys, und das Frontend hat den vollständigen Zustand ohnehin schon aus dem GET-Response.
- Admin-Passwort-Reset (Issue #5) nutzt bewusst denselben `passwordReset.ts`-Service wie der Self-Service-Flow (Issue #2), statt einer eigenen Admin-spezifischen Implementierung – gleiches Sicherheitsniveau (gehashter, einmal verwendbarer, befristeter Token), Admin sieht nie das tatsächliche Passwort, nur dass ein Reset ausgelöst wurde.

## Bekannte Probleme

- Docker-Setup (`docker-compose.yml`) ist ungetestet (kein Docker auf diesem System verfügbar) – inkl. des in Issue #3 ergänzten Volumes `herztiere_images_data`.
- Bild-URLs vom Fundtiere-Feed sind nur als Thumbnail bestätigt erreichbar (kein Vollbild-Pfad gefunden) – so übernommen (siehe Bild-Handling-Entscheidung oben).
- Ein Tier im Feed hat kein `<media:thumbnail>` (bestätigt in der Live-Stichprobe vom 2026-07-29) – wird vom Sync korrekt ohne Bild angelegt (`cached_image_path = null`); Frontend zeigt in diesem Fall einen Emoji-Platzhalter passend zur Kategorie (`AnimalCard`/`AnimalListCard`, `categoryEmoji()`), umgesetzt in Issue #4.
